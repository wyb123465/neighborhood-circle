## 官方接口口径

当前服务端适配器按官方文档使用以下接口：

- 地理编码 V3：`/geocoding/v3/`，地址转换为百度经纬度。
- 地点检索 V3：`/place/v3/around`，按中心点、半径和 query 检索 POI；适配器保留 V2 兼容开关。
- Direction API V2 步行路线：`/direction/v2/walking`，起终点参数使用 `纬度,经度`。
- 批量算路（RouteMatrix）V2：`/routematrix/v2/walking`，1 起点最多 45 终点（官方乘积上限 50 留余量），返回逐对 `distance/duration`（不含分段 steps）。体检路线证据与网格采样等时圈均走此接口，个人认证配额「批量算路 5,000 次/日」。

官方步行接口返回方案距离、耗时和分段步骤；适配器保留这些字段，不将 API 返回的耗时改写成固定步速。固定步速只用于项目自己的“居民采样点服务覆盖率”估计，二者在报告中必须分开。

## 配置原则

- `BAIDU_MAP_AK` 只放服务端 `.env`，不放 HTML、JavaScript、提交仓库或报告截图。`.env` 在导入 `backend.baidu` 时自动加载（`load_env_file()`），因此 README 里的「复制 `.env.example` 为 `.env` 并填 AK」是生效路径；缺少 python-dotenv 时降级为只读进程环境变量。
- 当前适配器使用 BD-09 经纬度；接口边界显式记录坐标类型，不能把本项目合成米制坐标传给百度。
- 每个请求设置超时；对相同 query 使用短期内存缓存；POI 分页有上限；在途并发有信号量限制，发起频率有 QPS 节流（当前默认 2 次/秒，`BAIDU_API_QPS` 可调）。
- 地点检索默认走 V3；V2 只作为显式兼容模式，不在默认路径静默回退，避免两个接口的字段和配额口径混在一起。
- HTTP 错误、百度 status 错误、超时和空结果都会转成可读错误；不把错误当成“没有设施”。
- 日志和 API 响应不记录 AK。当前没有把百度原始响应写入仓库，也没有声明其可再分发。

## 验证顺序

第 1 至 4 步可由 `scripts/check_live.py` 一次跑完（顺序调用、默认 narrow 画像、约 8 次调用、报告写入 `.runtime/`）。第 5 步已由 `tests/test_baidu.py` 的 fixtures 覆盖。手动逐步验证的顺序如下：

1. `/api/live/status` 确认只返回配置状态，不返回 AK，并核对 `configured` 与各画像的调用成本。
2. 地理编码验证一个结构完整的上海地址，记录 `precise`、`confidence`、`comprehension`。
3. POI 验证医疗、养老、教育、购物四类 query，检查分页、UID 去重和坐标类型。
4. 步行路线验证中心到若干 POI，记录 API distance/duration/steps 和请求耗时。
5. 对失败、超时、空结果、配额错误做 fixtures 测试。
6. 再将归一化的真实 POI 和路线输入空间采样算法；合成样例与真实模式保持明确标识。

**默认日配额（次/日）与并发（次/秒）**

| Web 服务 | 个人认证 | 企业（试用版） | 企业（授权版） |
| --- | --- | --- | --- |
| 地理编码 | 5,000 / 3 | 100,000 / 30 | 3,000,000 / 1,000 |
| 逆地理编码 | **300 / 3** | 100,000 / 30 | 3,000,000 / 1,000 |
| **地点检索** | **100 / 3** | 2,000 / 30 | 50,000 / 200 |
| 步行路线规划（轻量） | 5,000 / 3 | 100,000 / 30 | 300,000 / 200 |
| 批量算路 | 5,000 / 3 | 100,000 / 30 | 300,000 / 200 |

**这条决定了项目的可用性**：一次 `/api/live/inspect` 的调用成本是

- 地理编码 1 次；
- 地点检索 `CATEGORY_QUERIES` 展开后的 10 次（医疗 3 + 养老 3 + 教育 2 + 购物 2），每页算 1 次，分页时翻倍；
- 步行路线最多 `max_facilities` 次（接口默认 30）。

合计约 41 次/体检，其中真正卡死的是**地点检索**。个人认证下 100 次/日 ⇒ **每天只够跑 10 次完整体检**；企业试用版 2,000 次/日 ⇒ 200 次。逆地理编码个人仅 300 次/日，当前适配器未使用，若后续要加需一并核算。

**付费提升的资格限制**：官方明确「仅购买技术服务授权服务的企业认证开发者可在线购买配额流量包」。**个人认证无法在线购买配额包**，超限只能等次日零点重置。价格参考：基础服务/搜索 配额流量包 300 元 / 12 万次；并发提升 24~96 元 / QPS / 月；单服务包月 2 万，15 种套餐 6 万 / 月。

**由此确定的配置**：`BAIDU_API_MAX_CONCURRENCY` 默认取 **3**，`BAIDU_API_QPS` 默认取 **2**，给个人认证的 3 次/秒上限留出余量。原来默认 4 会超出个人认证并发上限并触发限流错误；企业认证账号可上调，但仍应低于账号实际配额。

**降低配额消耗：检索词组画像（已实施）**

`CATEGORY_QUERIES` 已按画像组织，`BAIDU_POI_QUERY_PROFILE` 选择，也可按次通过 `/api/live/inspect?query_profile=` 指定，`/api/live/status` 会回报每个画像的调用成本：

| 画像 | 地点检索次数/体检 | 检索词 | 个人认证下每天可跑 |
| --- | ---: | --- | ---: |
| `full`（默认） | 10 | 医院、社区卫生服务中心、药店 / 养老院、养老服务中心、老年人服务 / 小学、幼儿园 / 菜市场、超市 | 10 次 |
| `narrow` | 4 | 药店 / 养老院 / 小学 / 菜市场 | 25 次 |

`narrow` 的取舍是经过设计的：**赛题 40% 的评分项要求识别「1 公里内没有菜市场、药店或小学」的盲区，所以这三类必须保留**（同时保留演示主线养老），被放弃的只是子类细分（医院、社区卫生服务中心、幼儿园、超市、养老服务中心、老年人服务）。这意味着 `narrow` 不牺牲任何赛题明确要求的能力，只降低了子类召回精度。

响应里始终带 `parameters.query_profile` 与 `performance.query_profile`，使用 `narrow` 时 `warnings` 会追加一条说明，因此报告不会在画像上含糊。**正式测量与需要子类精度的结论必须用 `full`；`narrow` 只用于配额紧张的日常调试与答辩演示。**

尚未实施：把演示用的 POI 响应固化为可回放 fixture，避免重复演示持续消耗配额（须显式标注为回放，不得当作真实数据）。当前断网演示使用合成模式，不回放真实百度响应。

## 首次真实验收记录（2026-09-25）

**结论：整条真实链路已打通。** `scripts/check_live.py` 对官方接口的 8 次调用（1 地理编码 + 4 地点检索 + 3 步行路线）全部成功，共耗时 1.3 s，报告见 `.runtime/live-verification-20260925-114055.md`（不入库）。当日地点检索消耗 4 次/100 次。

**踩坑与修复（对部署方最重要的经验）**：`api.map.baidu.com` 同时有 IPv6（AAAA）解析；本机为移动家宽，httpx 默认按 getaddrinfo 顺序优先走 IPv6，百度看到的来源是家宽临时 IPv6 地址，而服务端 AK 的 IP 白名单只填了 IPv4 出口，于是恒报「APP IP校验失败」——此时控制台白名单无论怎么改 IPv4 都无效。修复：适配器新增 `BAIDU_API_FORCE_IPV4`（默认 `1`，通过 `httpx.HTTPTransport(local_address="0.0.0.0")` 绑定 IPv4 源地址）。测试注入的自定义 transport 不受该开关影响。

**字段核对**：geocoding v3 返回 `precise/confidence/comprehension/level`（本次 precise=0、confidence=30、comprehension=100、level=道路）；place v3 around 返回 `pois` 数组可分页；direction v2 walking 返回 `routes[0].distance/duration/steps`。与官方文档一致，未发现字段缺失。

**耗时参考（顺序调用）**：地理编码约 140 ms；地点检索 139–425 ms；步行路线 65–147 ms。家用宽带、非高峰时段，仅供量级参考，不作为性能结论。

**运维注意**：家宽 IPv4 出口会随重拨变化，若之后出现 403/IP 校验失败，先核对当前出口 IP 与白名单是否一致（强制 IPv4 已消除 v4/v6 混淆因素）。

**2026-10-02 复测记录**：在同一项目环境调用 `/api/live/inspect` 时，地理编码阶段收到 `APP IP校验失败`。服务端正确返回 502，没有生成或展示旧结果；这次复测说明出口白名单仍是交付现场的前置检查项，不否定 2026-09-25 官方接口 8 次调用成功的历史记录。

## 并发告警短信与 QPS 节流（2026-09-25）

**现象**：验收通过后收到官方短信——「路线规划服务并发量已接近约定上限（3/3），请登录官网提交工单」。

**根因**：此前把配额表的「并发(次/秒)」理解为在途并发，用信号量限制 3 个在途请求；但百度的口径是**每秒发起数（QPS）**。百米级响应时间下，3 个工作线程在 ~340ms 内就发起了 10 次路线请求（瞬时 ~30 QPS，超限 10 倍）；`check_live.py` 的「顺序调用」同样不受发起频率约束。这是两个被混淆的口径：信号量管在途，QPS 管发起。

**处置**：`_get_json` 增加发起间隔节流——任意两次真实网络请求的发起时刻间隔 ≥ 1/QPS（当前默认 2 次/秒，`BAIDU_API_QPS` 可调；缓存命中不进入节流、不占配额），信号量保留用于限制在途数量。单测以注入的 fake clock/sleep 验证「发起间隔依次排开」与「缓存命中旁路节流」两条性质。

**代价与对策**：节流后逐条算路的耗时会按次数线性化（10 条 ≈ 3.3s，原先 0.34s）——`/routematrix/v2/walking` 批量算路（1 次调用 ≤ 50 条）接入后即可收回，两者是配套工程，均已排入 roadmap。

**短信本身的定性**：自动预警，未扣配额、未限制账号，无需提交工单（工单是申请提额的通道）。但若继续超频，下一步就是真实的 QPS 拒绝——status 报错直接打断调用链，是演示现场风险。

## 批量算路的并发告警与对数拆块（2026-09-25，第二条短信）

**现象**：批量算路接入当天收到第二条官方短信——「批量算路服务并发量已接近约定上限（**10/3**）」。

**关键推断（实测证据，非文档口径）**：当时在飞的批量算路 HTTP 请求只有 1 个（1 起点 × 10 终点），而告警数值恰好是 10——说明**批量算路的并发按「每次请求内的路线对数」计入**，不是按 HTTP 请求个数。也就是说 1×24 的等时圈矩阵调用在百度侧等同 24 个并发算路单元。

**处置**：`walking_route_matrix` 按 `BAIDU_API_MATRIX_PAIRS`（默认 **3** 对/次）自动拆块、顺序发送，任何时刻并发对数 ≤ 个人认证上限；块间仍受 QPS 节流约束。`/api/live/inspect` 的 10 条设施路线变为 4 次矩阵请求（3+3+3+1），等时圈 24 个采样点变为 8 次。合并后行序与请求顺序保持一致（有单测锁定）。

**待确认**：对数计并发的口径是从告警数值反推的，尚需后续观察验证（例如 1×3 调用是否触发 3/3 告警、1×2 是否安静）。若确认属实，个人认证下批量算路的「每次调用省请求数」收益缩水为「省发起频次与 HTTP 往返」，配额账本应按对数口径重算——已同步修正页面上的配额提示。

**第三条观测、判定性实验与默认值调整（同日）**：3 对/次意味着每个请求都顶在 3/3 上限，实测随即出现 502「当前并发量已经超过约定并发配额，限制访问」。为区分「违规后的临时封禁」与「对数速率超线的实时拒绝」，做了判定性实验：静默 8 分钟 → 单次 1×2 探针**通过** → 紧接的持续流（对数速率 3/秒）**再次 502** → 把 `BAIDU_API_QPS` 默认降为 **2** 后，同样的持续流（28 次批量算路、27 秒）**一次通过**。结论：不存在独立的惩罚封禁，502 就是对数速率贴线/超线时的实时拒绝；持续运行必须低于 3 对/秒才有余量。据此 `BAIDU_API_QPS` 默认 2（配合按对数加权的节流，对数速率 = QPS = 2/秒），`BAIDU_API_MATRIX_PAIRS` 默认 2。
